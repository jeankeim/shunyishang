# 推荐逻辑考察 100 问

> 目标：逐条自查推荐链路的逻辑漏洞，用于优化 `packages/ai_agents` + `apps/api/routers/recommend.py`。
> 每条格式：**编号. [维度] 测试输入/场景** — 考察点 → 预期结果 ⚠️ 疑似漏洞（代码位置）。
> ⚠️ 标记表示我在阅读源码时发现的**高概率逻辑漏洞**，建议优先修复。

## 一、上下文提取（`_extract_context_from_query` / `_extract_context_by_rules`）

1. **输入「明天面试穿什么」** — 场景是否识别为「面试」；LLM 与规则两条路径结果是否一致？
2. **输入「25度多云去上班」** — 温度=25、天气=多云(土)、场景=商务 是否同时提取正确？
3. **⚠️ LLM 提取失败时** — 是否正确回退到 `_extract_context_by_rules`？回退后 travel_days/destination 是否仍能提取（LLM 分支与规则分支字段是否对齐）？
4. **输入「去三亚玩5天」** — travel_days=5、destination=三亚 是否都提取到？regex `(?:去|到|飞...)` 是否把「三亚」截断为「三」？
5. **⚠️ 输入「去哈尔滨」** — 目的地正则 `[\u4e00-\u9fa5]{2,4}?` + 后视 `(?=[出差旅游...])` 在无后续关键词时能否匹配到「哈尔滨」？
6. **输入「气温3度极寒」** — 温度=3 且 weather_desc=寒冷 是否都提取；温度正则 `\d+\s*[°度℃cC]` 是否漏掉裸数字「气温3」？
7. **⚠️ 前端已选场景=商务，但用户输入「和女朋友约会」** — `final_scene = extracted or scene` 会用「约会」覆盖「商务」，这是否符合"用户输入优先"的预期？误提取时无兜底。
8. **输入「37度」** — 高温是否触发；`weather_desc` 为空但温度极端时，weather_element 是否为 None（仅靠温度是否驱动后续极端温度逻辑）？
9. **⚠️ 输入「去北京出差」（无天数）** — 因 `travel_days is None` 不进旅行分支，退化为单日推荐，是否符合预期？「出差」却无多天规划。
10. **输入「三天两夜去成都」** — 中文/阿拉伯数字混合，`day_match` 先匹配「三天」还是被「两夜」干扰？
11. **输入「去外面走走」** — 「外面」应被 `non_city_words` 过滤，验证 destination=None。
12. **⚠️ LLM 提取的 weather_info 与外部传入 weather_element 不一致时** — `final_weather_info=extracted or weather_info`、`final_weather_element=extracted or weather_element` 分别取值，会不会出现"温度来自 query、五行来自外部"的错配？
13. **输入「下雨天去健身房」** — 天气=雨天(水) + 场景=运动，运动优先级是否压过其它？
14. **同一句话包含两个城市「从北京去上海」** — destination 取的是哪个？逻辑是否明确。
15. **输入纯 emoji / 空字符串** — 提取器是否安全降级，不抛异常。

## 二、场景识别与优先级（`_extract_context_by_rules` if-elif 链）

16. **⚠️ 输入「去三亚出差顺便游泳」** — 同时命中出差/度假/运动，if-elif 短路后只保留最先命中的「出差」，运动被吞。规则声称"运动优先"但代码顺序上出差在前，冲突。
17. **输入「商务旅行」** — 是否被「出差」正确捕获而非「旅行」/「商务」？验证注释所述顺序。
18. **输入「去海边度假」** — 命中「度假」还是「旅行」（"去+城市"分支）？
19. **输入「公司团建爬山」** — 「爬山/登山」应归户外探险，验证未被「上班/工作」误判。
20. **输入「在家办公」** — 「办公」→商务 与「在家」→居家 冲突，取哪个？
21. **⚠️ 输入「婚礼当天要跑去健身」** — 婚礼 vs 运动，验证优先级是否有明确业务定义。
22. **输入「party 派对」** — 中英文混合关键词是否命中派对。
23. **⚠️ LLM 分支的 scene_mapping 缺「户外探险」自身映射** — LLM 返回「户外探险」时 `scene_mapping.get(scene, scene)` 透传，验证与规则分支是否等价。
24. **多维场景识别 `extract_scene_multidimensional`** — main_scene / sub_scene / emotion 三者，`analyze_intent_node` 里 `state.scene or main_scene` 优先级是否正确。
25. **输入无任何场景词「随便看看」** — scene=None，验证后续 scene_weight=0 时不会误算 scene_score。
26. **输入「见客户」** — 归商务，验证与「约会/相亲/见面」的「见面」不冲突。
27. **子场景传递** — `sub_scene` 从 `analyze_intent_node` 到 `retrieve_items_node`、`_build_scene_filter` 是否全程传递未丢失？
28. **场景=运动时的功能硬过滤** — `_build_scene_filter` 要求 `functionality->>'透气/速干/运动/弹性'=true`，若库中运动装未打这些标签会否被全部过滤为空？

## 三、天气 / 温度逻辑（`_build_weather_filter` / `_calculate_temp_score` / 温度硬过滤）

29. **⚠️ 极端温度定义不一致** — `is_extreme_temp` 用 `≤5 或 ≥32`（触发温度权重 0.25），而硬过滤用 `≥30/≥25/≤0/≤10`。31℃ 时不加温度权重却已硬排除厚重/中厚，逻辑割裂。
30. **⚠️ 温度硬过滤仅在 `temp_filtered` 非空时生效** — 若某温度下所有物品都被排除，则回退到"完全不过滤"，可能给严寒天推荐短袖。验证该兜底是否合理。
31. **温度=28℃** — 落在 `≥25 排除厚重` 与 `_calculate_temp_score` 的"适中(else)+0.2"之间，验证评分与过滤是否协调。
32. **⚠️ 名称含「羊毛」但 DB 标 thickness=轻薄** — 硬过滤以名称覆盖为「厚重」，但 `_calculate_temp_score` 仍用 DB 的「轻薄」算分，导致过滤与评分依据不同源。
33. **temperature=None（只有天气描述）** — `_calculate_temp_score` 返回 0.5，验证温度权重是否被浪费。
34. **温度=5℃（边界）** — `is_extreme_temp` 为 True（≤5），但硬过滤 `≤10 排除极薄` 而非 `≤5` 分支，验证边界物品命运。
35. **`_build_weather_filter` SQL 温度区间重叠** — `<15` 与 `<25` 分支的 thickness 集合有交集，验证 SQL 过滤是否过宽/过窄。
36. **雨天** — 天气硬过滤已被注释掉（改为软评分），验证雨天是否真的会推防水单品，还是仅靠向量语义。
37. **`temperature_range->>'最低'` 为字符串比较风险** — SQL 里 `(temperature_range->>'最低')::int`，若 JSON 中该字段缺失或非数字是否报错。
38. **温度安全检查阶段** — 极端温度下替换 `temp_score<0.3` 的物品，补充来源 `scored_items`，是否可能重新引入被场景/类目多样性排除的物品？
39. **高温 37℃ + 场景=运动** — 温度硬过滤（排厚重/中厚）与运动功能过滤叠加后候选是否过少。
40. **weather_element 映射固定表** — 「晴天→火」在冬天晴冷天是否合理？考察 weather_element 只由描述决定、不结合温度的局限。
41. **多云→土** — 验证「土」进入 target_elements 后对结果的实际影响是否符合预期。
42. **wind_level / humidity 仅用于 LLM 文案** — 不进入评分与过滤，验证是否遗漏了对推荐的实际影响。

## 四、八字 / 喜用神 / 忌神 / 流年 / 大运合并（`merge_recommendations` + `analyze_intent_node`）

43. **优先级验证** — 八字喜用神 > 天气 > 场景 > 意图，构造四者冲突输入，验证最终 target 顺序。
44. **⚠️ target 截断为 3 个** — `list(dict.fromkeys(elements))[:3]`，若喜用神已占 2 个 + 天气 1 个，则场景/意图五行永远进不来，验证是否合理。
45. **忌神=天气五行且相生喜用神** — 应进 `boost_elements` 而非 target，验证 `_check_generates_xiyong`。
46. **忌神=天气五行且不生喜用神** — 应被直接跳过（既不进 target 也不进 boost），验证。
47. **⚠️ 流年幸运元素追加** — `analyze_intent_node` 里流年 lucky 最多加 2 个到 target，但 target 已在 merge 时截断为 3，此处 append 会突破 3 个上限，验证 target 是否可能变成 5 个。
48. **流年 lucky 元素是忌神** — 应跳过不加入 target，验证 `elem in avoid_elements` 分支。
49. **无八字输入** — xiyong_elements=[]、avoid_elements=[]，验证纯场景/意图推荐是否正常。
50. **八字计算异常** — `calculate_bazi` 抛错后 bazi_result=None，验证降级路径不崩。
51. **⚠️ 八字缓存键** — `bazi:{year}:{month}:{day}:{hour}` 不含 gender，男女同生辰会命中同一缓存，但喜用神算法是否依赖 gender？若依赖则缓存串号。
52. **大运计算** — `current_age = current_year - birth_year` 未考虑生日是否已过，验证年龄误差 1 岁对大运的影响。
53. **added_elements 计算** — `target 中不在 xiyong 的即为 added`，验证天气/场景/流年元素是否都正确归类为 added。
54. **boost_elements 去重** — 天气、场景、意图都可能加同一 boost 元素，验证 `if elem not in boost_elements` 去重完整。
55. **意图推断仅 method=='rule' 才并入** — LLM 意图结果被忽略，验证是否有意为之。
56. **`suggested_elements` 为空** — 八字算出空喜用神时，target 是否会全空导致后续五行分全 0。
57. **流年 `overall_score` / `outfit_advice`** — 注入 bazi_reasoning 文案，验证空值时不出现「运势0分」误导。
58. **喜用神与忌神有交集（数据异常）** — 若同一元素既在 suggested 又在 avoid，merge 行为如何？考察防御。

## 五、五行评分（`retrieve_items_node` 打分段）

59. **⚠️ wuxing_score 可超过 1.0** — primary(0.6)+secondary(0.3)+boost(0.08+0.04)+wear_count(0.1)=1.12，与其它 0–1 维度加权时被放大，破坏权重语义。建议归一化。
60. **⚠️ wear_count 加分混入 wuxing_score** — `wuxing_score += max(0, 0.1 - wear_count*0.02)`，穿着次数本应独立维度，混进五行分导致"没穿过的忌神单品"也可能加分。
61. **primary 命中 + secondary 也命中 target** — 0.6+0.3=0.9，验证是否符合"主属性权重更高"设计。
62. **⚠️ boost 元素加分** — 忌神但生喜用神的单品 +0.08，是否可能让忌神单品排到喜用神单品之前？构造对比用例。
63. **semantic_score 缺省 0.5** — 向量搜索失败/无 embedding 时全为 0.5，验证是否退化为仅靠 wuxing/scene 排序。
64. **scene_score 缺省 0.5 且 `>0` 才保留** — 验证 `calculate_scene_match_score` 返回 0 时的硬排除是否误伤中性单品。
65. **preference_score 异常降级 0.5** — `calculate_preference_score` 抛错回退，验证不影响整体排序稳定。
66. **final_score 加权和是否恒等于各维度点积** — 抽查一条结果手工核算 final_score，验证无计算错误。
67. **wear_count 为 None / 负数** — `isinstance` 与 `>=0` 判断，验证脏数据不加分也不报错。
68. **全部候选 wuxing_score==0** — 触发降级"按 semantic 排序"，验证降级后仍走类目多样性。
69. **同分排序稳定性** — 多个 final_score 相同的物品，`sort` 顺序是否可复现（影响缓存一致性）。
70. **primary_element 为空字符串** — `"" in target_elements` 恒为 False，验证无属性单品得 0 分是否合理。

## 六、权重体系（`_WEIGHT_PRESETS` / `_compute_recommend_weights`）

71. **8 种组合权重和=1.0** — 逐个校验 `(has_bazi,has_scene,has_prefs)` 预设总和精确为 1。
72. **⚠️ 极端温度重算后浮点修正** — `preset["semantic"] += (1.0-total)` 兜底，验证极端组合下 semantic 不会被修正成负数或异常值。
73. **has_prefs 依赖 user_id** — 未登录用户 pref_weight=0，验证匿名与登录用户结果差异是否符合预期。
74. **⚠️ pref_weight>0 但 user_prefs 获取失败** — `has_prefs=bool(user_prefs)` 为 True 但 `calculate_preference_score` 每条都异常→全 0.5，等于白占 10%~15% 权重稀释其它维度。
75. **有八字无场景（True,False,*）** — wuxing 权重最高（0.35~0.45），验证纯八字场景是否过度依赖五行。
76. **无八字无场景无偏好** — semantic 0.6 + wuxing 0.4，但此时 target_elements 从何而来（仅意图）？验证 wuxing 0.4 是否有意义。
77. **极端温度 + 无八字无场景** — temp 占 0.25，其余按比例缩放，验证 wuxing 缩放后是否过小到失效。
78. **scene_weight=0 但 scene 存在** — 某些预设 scene 权重为 0（如无八字有场景仍给 0.20？核对），验证 scene_score 是否被计算却不参与加权。
79. **权重预设兜底** — 非法组合回退 `(False,False,False)`，验证 key 一定命中不会走兜底。
80. **temp_weight 仅极端温度>0** — 非极端温度时温度完全不参与加权，仅靠硬过滤，验证 20~24℃ 舒适区推荐是否合理。

## 七、检索模式（public / wardrobe / hybrid，`retrieve_items_node`）

81. **wardrobe 模式无 user_id** — 应返回明确错误，验证。
82. **wardrobe 模式衣橱为空** — 返回"请先添加衣物"，不 fallback 公共库，验证。
83. **⚠️ wardrobe 模式五行全不匹配** — 返回"衣橱无符合五行"错误，但用户可能只想按语义推荐，验证是否过于严格。
84. **hybrid 模式去重** — 衣橱与公共库同一 item 是否按 `id` 去重（衣橱用 id，公共用 item_code，键不同源，验证不会重复）。
85. **⚠️ hybrid 模式 item_sources 键不一致** — 衣橱用 `str(id)`、公共用 `item_code`，最终 `top_items` 回写 source 时键混用，验证前端 source 标记是否错乱。
86. **public 模式空结果** — 走 `_get_versatile_items` 百搭兜底，验证兜底单品 source 标记为 public。
87. **hybrid 衣橱结果已够 top_k** — 是否还会多余查询公共库？验证 `len(items)<top_k` 短路。
88. **top_k 默认值不一致** — 缓存键用 `top_k or 10`，agent 用 `top_k or 5`，验证同一请求缓存与计算的 K 是否错位。
89. **limit=50 vs top_k** — public 取 50 候选再截 top_k，wardrobe 取 50、hybrid 取 top_k，验证候选池大小差异对多样性的影响。
90. **embedding 生成失败** — wardrobe/hybrid 依赖 `generate_embedding`，异常时是否安全降级。

## 八、多样性 / 过滤 / 缓存 / 旅行

91. **类目多样性上限** — 核心服装每类≤2、配饰/鞋履≤1，验证 top_k=5 时不会返回 5 件上装。
92. **⚠️ 强制塞入配饰** — 无配饰时替换最低分核心服装，验证是否会挤掉更高分的必要单品（如严寒天挤掉唯一外套）。
93. **五行多样性最多替换 1 件** — 全同五行时替换最低分同五行单品，验证替换后不破坏温度/场景安全。
94. **⚠️ 多样性替换绕过温度安全** — `_ensure_wuxing_diversity` 从 `all_scored` 取替换项，可能引入 temp_score 低的单品，验证极端温度下是否被后置的温度安全检查纠正。
95. **gender=None 排除女性专属** — SQL `gender IN (中性,男,NULL)`，验证女性未填性别时是否被误推男装。
96. **⚠️ 缓存键缺失关键字段** — `cache_key` 不含 `weather`(温度)、`travel_days`、`destination`、`luggage_size`、`gender`，验证：同 query 不同温度/不同目的地/不同天数会命中同一缓存返回错误结果。**（高危）**
97. **缓存命中返回一次性 reason** — 命中时 token 一次性返回而非流式，验证前端渲染兼容。
98. **⚠️ 缓存写入条件** — 仅 `collected_analysis and collected_items` 才写缓存，旅行 travel_plan 事件未纳入收集，验证旅行结果是否根本不进缓存 / 或进了却丢 travel_plan。
99. **旅行触发条件** — `scene in (旅行,出差,度假,户外探险) and days>=2`，验证「出差1天」「旅行但无天数」不误触发多天规划。
100. **⚠️ 旅行物品池注入** — `travel_item_pool = scored_items[:max(20, top_k*4)]`，取的是过滤/多样性处理**前**的 scored_items，验证多天规划用的物品是否已通过温度/场景硬过滤（否则旅行方案可能含被排除的单品）。
